# CH01 — RCC/PLL 100MHz 클럭 설정 및 오실로스코프 실측 검증

> **한 줄 요약:** HAL 없이 레지스터 조작만으로 SYSCLK 100MHz를 구성하고,
> MCO2 출력을 오실로스코프로 실측하여 **이론값 대비 오차 +1.85%** 로 검증했다.
> 이 과정에서 3건의 계측 오류를 순차적으로 진단·해결하며 측정 신뢰성을 확보했다.

---

## 1. 목표

- HSI 16MHz → PLL → **SYSCLK 100MHz** 구성 (STM32F411 최대 동작 주파수)
- 설정된 클럭이 "코드상으로만 100MHz"가 아니라 **물리적으로 실재하는지** MCO2(PC9) 핀 출력을 통해 계측기로 증명
- 클럭 설정 시퀀스의 순서 의존성(VOS → Flash latency → PLL → 버스 분주 → SW 전환)을 이해하고 구현

## 2. 구현

### 2.1 PLL 파라미터 설계

| 파라미터 | 값 | 근거 |
|---|---|---|
| PLLM | 8 | VCO 입력 = 16MHz / 8 = **2MHz** (RM0383 권장 1~2MHz 상한) |
| PLLN | 100 | VCO 출력 = 2MHz × 100 = **200MHz** (허용범위 100~432MHz) |
| PLLP | /2 | SYSCLK = 200MHz / 2 = **100MHz** |
| AHB | /1 | HCLK = 100MHz |
| APB1 | **/2** | F411 APB1 최대 50MHz 제약 준수 |
| APB2 | /1 | 100MHz |

### 2.2 순서가 강제되는 설정 시퀀스

```c
/* 1) PWR 클럭 인에이블 + VOS Scale 1 — 100MHz 동작의 전제조건 */
RCC->APB1ENR |= RCC_APB1ENR_PWREN;
(void)RCC->APB1ENR;                     /* 에라타 대응 더미 리드 */
PWR->CR |= PWR_CR_VOS;

/* 2) Flash 3WS — PLL 전환 "전에" 반드시. 순서 위반 시 하드폴트 */
FLASH->ACR = FLASH_ACR_LATENCY_3WS
           | FLASH_ACR_PRFTEN | FLASH_ACR_ICEN | FLASH_ACR_DCEN;
while ((FLASH->ACR & FLASH_ACR_LATENCY) != FLASH_ACR_LATENCY_3WS) { }

/* 3~7) HSI 확인 → PLL 설정/기동 → 버스 분주 → SW=PLL 전환 (main.c 참조) */
```

**설계 노트**
- `RCC->AHB1ENR` 인에이블 직후의 더미 리드는 STM32F4 에라타
  *"Delay after an RCC peripheral clock enabling"* 대응이다. AHB 버스 지연으로
  인에이블 직후 페리페럴 레지스터 쓰기가 무시될 수 있다.
  **HAL이 내부적으로 처리해주는 것을 레지스터 레벨에서는 직접 책임져야 하는 대표 사례.**
- `GPIOA->MODER`는 리셋값이 `0xA8000000`으로 PA13/PA14(SWD)가 AF 설정되어
  있으므로, 전체 쓰기가 아닌 read-modify-write로만 조작했다.
  (전체 쓰기 시 디버거 연결이 끊긴다.)

### 2.3 검증 경로 — MCO2

PC9를 AF0(MCO2)으로 설정, SYSCLK/5를 출력:
- 이론 출력 = 100MHz / 5 = **20MHz** (주기 50ns)
- 프리스케일러를 /5로 둔 이유: 100MHz 원신호는 프로브/스코프 대역폭 한계에서
  파형 무결성을 확보하기 어려우므로, 검증 가능한 주파수 대역으로 낮춰 출력

## 4. 계측 문제 해결 기록 — 3건

측정 초기에 **물리적으로 불가능한 값들**(74MHz, 34MHz, Pk-Pk 7.6V, 최저점 -2.24V)이
관측되었다. F411의 최대 클럭이 100MHz이므로 74MHz×5=370MHz는 존재할 수 없는
신호라는 판단에서 출발하여, 원인을 순차적으로 분리·제거했다.

| # | 증상 | 원인 | 해결 | 판별 근거 |
|---|---|---|---|---|
| 1 | 20MHz 사각파가 사인파처럼 뭉개짐 | 스코프 **대역제한 필터(20MHz)** 활성 상태 | 필터 OFF | 측정 대상 주파수와 필터 차단 주파수가 일치 → 고조파 소실 |
| 2 | 진폭이 측정마다 요동 (1V~7.6V) | 프로브 팁 ↔ 핀헤더 **접촉 불량** | M-F 점퍼로 기계적 고정 | DMM 평균전압은 안정(1.3V) ↔ 스코프 순간값만 요동 → 접촉 경로 문제로 특정 |
| 3 | 최저점 **-2.24V** 등 물리적 불가능 값 | **그라운드 리드 인덕턴스** (긴 악어클립) | 프로브 슬리브 제거 후 단축 점퍼로 그라운드 직결 | GPIO는 0~3.3V만 출력 가능 → 음전압은 계측 아티팩트로 확정. 조치 후 첨두치 3.64V로 안정화 |

**교훈:** 주파수/주기 측정은 제로크로싱 타이밍 기반이라 위 오류들의 영향을 적게 받아
일관된 값(20.3~20.4MHz)을 유지한 반면, 순간 전압 측정은 그라운드 경로와 접촉 품질에
직접적으로 좌우되었다. **계측기가 표시하는 숫자를 그대로 믿지 않고, 물리적 타당성으로
교차검증하는 습관**이 이 챕터의 실질적 산출물이다.

## 5. 한계

- 사용 장비(TDS224, 100MHz 대역폭·1GS/s)에서 20MHz 신호의 파형 미세 형상(모서리
  샤프니스)은 실시간 샘플링 한계로 완전한 재현이 어렵다. 본 챕터의 결론은 파형
  형상이 아닌 **주파수 정량 측정**에 근거한다.
- HSI 기반이므로 ±1~2% 수준의 주파수 오차는 원리적으로 제거 불가.
  정밀 클럭이 필요한 응용(USB 등)은 HSE가 전제되어야 함을 확인했다.

  # CH02 — GPIO 드라이버 설계, OSPEEDR 슬루레이트 실측, 함수 추상화 비용 정량화

> **한 줄 요약:** 레지스터 레벨 GPIO 드라이버를 직접 설계하고 두 가지 실험을 수행했다.
> ① OSPEEDR 4단계 실측 — **무부하 조건에서는 설정 간 차이가 발현되지 않음**을 확인하고
> 부하 의존성으로 원인을 규명했다. ② 함수 추상화 비용 벤치마크 — 별도 컴파일 단위의
> 함수는 -O2에서도 **4.8배** 느렸으나, `static inline` 전환으로 **레지스터 직접 접근과
> 완전히 동일한 성능(5 cycles/toggle)** 을 달성했다.

---

## 1. 목표

1. 재사용 가능한 GPIO 드라이버(`my_gpio.h/.c`)를 레지스터 레벨로 설계
2. OSPEEDR(슬루레이트) 4단계가 상승시간/오버슈트에 미치는 영향 실측
3. "함수로 감싸면 느려진다"는 통념을 **DWT 사이클 카운터로 정량화**하고,
   극복 방법(`static inline`)까지 실증

## 2. 실험 A — OSPEEDR 슬루레이트 실측

### 2.1 방법

- 대상: PC8 (외부 회로가 전혀 연결되지 않은 자유 핀 — LD2처럼 LED/저항이
  달린 핀은 파형 왜곡으로 배제)
- BSRR 토글 루프로 구형파 생성, OSPEEDR을 00→11로 변경하며 4회 반복 측정
- 상승시간: 사용 장비(TDS224)에 자동 Rise Time 측정 기능이 없어
  (TDS2MM 확장모듈 필요) **Voltage 커서로 10%/90% 레벨(0.36V/3.16V)을 산출한 뒤
  Time 커서로 ΔT를 수동 측정**하는 표준 절차를 수행

### 2.2 결과

| OSPEEDR | 첨두치 | 상승시간 (10–90%) |
|---|---|---|
| 00 (Low) | 3.52V | **82ns** |
| 01 (Medium) | 3.52V | ~80ns (오차범위 내 동일) |
| 10 (Fast) | 3.52V | 동일 |
| 11 (High) | 3.52V | 동일 |

### 2.3 분석 — 왜 차이가 없는가

4단계 모두 동일 값으로 수렴한 것은 오측정이 아니라 **부하 조건의 귀결**이다.

- 슬루레이트 제어의 본질은 출력 드라이버의 구동 능력(등가 임피던스 R) 조절이며,
  상승시간은 **τ ≈ R × C_load** 에 지배된다.
- 본 실험의 부하는 프로브 입력 커패시턴스(10x 프로브, 십수 pF)뿐으로,
  데이터시트 슬루레이트 스펙의 표준 시험 조건(≈50pF)보다 훨씬 가볍다.
- **C_load가 충분히 작으면 R의 차이가 τ에 유의미하게 반영되지 않는다** —
  4단계가 82ns 부근으로 수렴한 것은 이 조건에서 이론적으로 예측되는 결과다.

**실무적 시사점:** 슬루레이트 설정의 효과는 부하 의존적이다. 버튼·LED처럼
가벼운 부하의 GPIO에 High 설정을 쓰는 것은 속도 이득 없이 EMI 방사 리스크만
키우는 선택이며, **"요구 속도를 만족하는 최저 슬루레이트"가 올바른 기본값**이다.
가전제품은 EMI 인증이 출하의 실제 관문이므로 이 원칙의 무게가 크다.

## 3. 실험 B — 함수 추상화 비용 정량화

### 3.1 방법

- DWT 사이클 카운터(`CYCCNT`)로 10,000회 토글 소요 사이클 측정
- 3가지 구현 × 2가지 최적화 레벨 매트릭스 비교
- 컴파일러의 루프 제거를 막기 위해 결과 변수를 `volatile`로 선언

### 3.2 결과 (cycles/toggle, N=10,000)

| 구현 방식 | -O0 | -O2 |
|---|---|---|
| 레지스터 직접 (`GPIOC->BSRR = ...`) | 20 | **5** |
| 드라이버 함수 — 별도 `.c` 파일 | 70 | **24** |
| 드라이버 함수 — 헤더 `static inline` | — | **5** |

### 3.3 분석

- **-O2에서도 4.8배 차이가 남는 이유:** GCC는 링크 타임 최적화(LTO) 없이는
  **다른 컴파일 단위(translation unit)의 함수를 인라인하지 않는다.**
  `my_gpio.c`에 구현된 함수는 호출(call/return) 오버헤드가 그대로 잔존했다.
- **`static inline` 전환 효과:** 함수 본문을 헤더로 이동해 호출부와 같은
  컴파일 단위에 두자, -O2에서 **레지스터 직접 접근과 1 cycle 이내로 동일**해졌다.
- 이는 CMSIS를 포함한 임베디드 라이브러리들이 저수준 접근자를 헤더에
  inline으로 구현하는 설계 관행의 근거를 직접 재현한 것이다.

**결론:** "추상화 = 성능 손실"은 조건부 명제다. 컴파일 단위 배치를 이해하고
`static inline`을 적용하면, **가독성·재사용성·타입 안전성을 가진 드라이버
계층을 제로 코스트로 구축할 수 있다.**

## 4. 산출물

- `my_gpio.h` — `static inline` 접근자 + 초기화 API (재사용 가능, 이후 챕터의 기반)
- `dwt.h` — 사이클 정밀 벤치마크 유틸리티 (10ns 분해능 @100MHz)

## 5. 한계 및 후속 계획

- 슬루레이트 실험은 무부하 단일 조건이므로, 표준 부하(수십 pF) 조건에서의
  단계별 차이 분화는 검증하지 못했다. 부하 커패시터를 추가한 조건별 재실험은
  후속 과제로 남긴다.
- HAL(`HAL_GPIO_TogglePin`) 동일 조건 비교는 HAL 미포함 프로젝트 구성상
  제외했다. 별도 브랜치에서의 비교를 후속 과제로 남긴다.
